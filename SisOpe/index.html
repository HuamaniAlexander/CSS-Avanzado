// 01 — FUNDAMENTOS

¿Qué es un Sistema Operativo?

El SO actúa como intermediario entre tú (usuario) y el hardware. Es el director de orquesta que coordina todo.

👤 Usuarios / Programas
📦 Programas de Aplicación
⚡ System Calls (API)
🧠 Kernel del SO
💾 Hardware (CPU, RAM, Discos)

← Haz click en una capa

Cada capa tiene un rol específico. El SO (Kernel) es el puente entre el software y el hardware real.

🎯

Para el Usuario

Busca comodidad y facilidad de uso. El usuario no se preocupa por cómo se reparten los recursos internamente — solo quiere que sus programas funcionen.

⚙️

Para el Sistema

El SO es un asignador de recursos. Decide cómo usar el hardware de forma eficiente para que todos los usuarios y programas estén satisfechos.

📱

Sistemas Móviles

En tablets y smartphones (iOS, Android), el SO se optimiza para duración de batería, pantallas táctiles y sensores adicionales como GPS y giroscopio.

🚗

Sistemas Embebidos

En autos o electrodomésticos, el SO funciona casi sin intervención del usuario. Opera con restricciones de tiempo muy estrictas.

Servicios que ofrece el SO

🖥️

Interfaz de Usuario (UI)

▼

El SO puede ofrecer distintas formas de interacción:

  • CLI (Command Line Interface): Línea de comandos. Preferida por administradores por su eficiencia y capacidad de automatización con scripts. El intérprete se llama Shell.
  • GUI (Graphical User Interface): Iconos, ventanas y ratón. Facilita el uso para usuarios generales.
  • Pantallas Táctiles: Gestos, teclados virtuales y comandos de voz.
📁

Sistema de Archivos

▼

El SO gestiona el almacenamiento de datos: crear, borrar, leer y escribir archivos y directorios, así como los permisos de acceso a cada uno.

open() → read() → write() → close()
🔒

Protección y Seguridad

▼

El SO controla el acceso a la información y defiende el sistema contra accesos no válidos. Para esto usa el concepto de modo dual:

  • User Mode (bit=1): Privilegios limitados. Tus apps normales corren aquí.
  • Kernel Mode (bit=0): Acceso total al hardware. Solo el SO corre aquí.
⚡ Transición: Cuando una app necesita un servicio del SO (abrir un archivo), genera un System Call → el bit cambia a 0 (Kernel) → realiza la tarea → vuelve a bit 1 (User).
📡

Llamadas al Sistema (System Calls)

▼

Son la interfaz que permite a los programas de usuario solicitar servicios al kernel. Los desarrolladores usan APIs (POSIX, Win32) para no manejar detalles complejos de hardware.

fork() // crear proceso
exit() // terminar proceso
open("/archivo") // abrir archivo
getpid() // obtener ID del proceso

Arquitectura básica: La CPU, los controladores de dispositivos (disco, pantalla, teclado) se conectan mediante un bus común para acceder a la memoria compartida (RAM).
🧠

CPU

Ejecuta instrucciones. Solo puede acceder directamente a la RAM. Puede trabajar simultáneamente con controladores de dispositivos.

💾

RAM (Memoria Principal)

Único almacenamiento de gran tamaño con acceso directo de la CPU. Es volátil — pierde datos al apagar.

🎮

DMA — Acceso Directo

Para dispositivos de alta velocidad. El controlador mueve bloques de datos directo a RAM sin interrumpir la CPU en cada byte. Solo interrumpe al terminar el bloque.

🔄
SMP — Simétrico

Multiprocesador Simétrico

Cada procesador realiza todas las tareas del SO. Todos los procesadores son iguales y comparten bus, reloj y memoria. Es el más común hoy.

👑
Asimétrico

Multiprocesador Asimétrico

Modelo maestro-esclavo. Un procesador master controla el sistema, los esclavos ejecutan tareas específicas. Menos flexible.

⚡
Multi-core

Diseño Multinúcleo

Múltiples núcleos de CPU en un solo chip. Más eficiente en consumo de energía y velocidad que múltiples chips separados.

⚡ Ventajas clave: Mayor rendimiento, economía de escala y mayor fiabilidad (si una CPU falla, el sistema sigue funcionando, aunque más lento).
Clustered ≠ Multiprocesador: Aquí son varias computadoras independientes trabajando juntas, generalmente conectadas por una red de área de almacenamiento (SAN).
🛡️

Alta Disponibilidad

Si un nodo cae, otro toma su lugar automáticamente. Diseñados para sobrevivir a fallas hardware.


Asimétrico: Una máquina en "espera activa" (hot standby) monitorea el servidor activo.

Simétrico: Todos los nodos ejecutan aplicaciones y se monitorean entre sí.

🌐

Casos de Uso

Bases de datos de alta disponibilidad, servidores web de gran tráfico, computación científica distribuida, y aplicaciones críticas que no pueden permitirse tiempo de inactividad.

☁️

Computación en la Nube

▼

Ofrece recursos (CPU, almacenamiento, apps) como un servicio por red, basado en virtualización y pago por uso.

  • Pública: AWS, Google Cloud, Azure — disponible para todos.
  • Privada: Infraestructura dedicada a una organización.
  • Híbrida: Combina pública y privada.
🔗

Peer-to-Peer (P2P)

▼

No hay jerarquía fija. Cada nodo puede actuar como cliente, servidor o ambos. Ejemplo clásico: Skype, BitTorrent. Muy resiliente — no hay un punto central de fallo.

⏱️

Tiempo Real (Embedded)

▼

Sistemas con restricciones de tiempo fijas y estrictas. Si no cumple el plazo (deadline), el sistema falló.

  • Hard Real-Time: Frenos ABS de un auto. Fallar el deadline = catástrofe.
  • Soft Real-Time: Streaming de video. Un retraso es molesto pero no catastrófico.
// 03 — CORAZÓN DEL SO

Interrupciones

El SO está "impulsado por interrupciones". Sin este mecanismo, el sistema no podría manejar múltiples dispositivos eficientemente.

¿Cómo funciona?

1. CPU ejecutando proceso

La CPU está ocupada ejecutando instrucciones de un programa normalmente.

2. Dispositivo termina tarea

Un dispositivo (teclado, disco, red) termina una operación y envía una señal de interrupción al bus.

3. CPU guarda estado

La CPU pausa lo que está haciendo y guarda su estado actual (registros, contador de programa) en memoria.

4. Ejecuta ISR

La CPU ejecuta la rutina de servicio de interrupción (ISR) correspondiente al dispositivo.

5. Retoma trabajo original

Restaura el estado guardado y continúa el proceso original como si nada hubiera pasado.

Tipos de interrupción

🖥️

Interrupción de Hardware

▼

Generada por un dispositivo físico para avisar que terminó una tarea o que necesita atención.

  • Tecla presionada en el teclado
  • Disco terminó de leer un sector
  • Paquete de red recibido
  • Timer del sistema expiró
💥

Trap / Exception (Software)

▼

Interrupción causada por software. Puede ser:

  • Error: División por cero, acceso a memoria inválida.
  • System Call: Un programa pide un servicio al kernel (abrir archivo, crear proceso).
Importante: Un System Call es básicamente un trap intencional — el programa dice "necesito que el kernel haga esto por mí".

E/S: ¿Síncrona o Asíncrona?

⏳
SÍNCRONA

El control vuelve al usuario solo cuando termina la E/S. La CPU queda inactiva o en bucle de espera. Simple pero ineficiente.

⚡
ASÍNCRONA

El control vuelve inmediatamente. La CPU sigue con otras cosas. El programa consulta después si terminó (System Call).

El Principio de Caché

Se copia temporalmente información de un almacenamiento lento a uno más rápido para que la CPU trabaje mejor.

Primero revisa caché (nanosegundos).

Cache HIT

Dato encontrado → uso inmediato ✅

Cache MISS

No está → busca en RAM → copia a caché para futuras consultas.

🔄

Multiprogramación y Multitarea

MULTIPROGRAMACIÓN

El SO organiza varios trabajos para que la CPU siempre tenga algo que ejecutar. Si un proceso espera (E/S), cambia a otro.

MULTITAREA (Time-sharing)

Evolución de la multiprogramación. La CPU cambia de trabajo tan rápido que el usuario siente que interactúa con todos los programas al mismo tiempo.

Un proceso cambia de estado según lo que esté pasando: esperando CPU, esperando E/S, ejecutando, etc.

📋

PCB — Process Control Block

Cada proceso tiene un PCB donde el SO guarda toda la información para gestionarlo:

  • PID — Identificador único del proceso
  • Estado — New/Ready/Running/Waiting/Terminated
  • Program Counter — Próxima instrucción a ejecutar
  • Registros CPU — Estado del procesador guardado
  • Prioridad — Para el planificador
  • Archivos abiertos — Lista de recursos en uso
🔀

Context Switch — Cambio de Contexto

Cuando la CPU cambia de proceso:

Guardar estado del proceso A

Registers, PC, memoria → guardados en el PCB de A.

Cargar estado del proceso B

Se restaura el PCB de B en la CPU.

Overhead ⚠️

Durante el cambio, el sistema no hace trabajo útil. Por eso se minimiza la frecuencia.

📋

FCFS — Primero en llegar, primero en ser atendido

▼

El algoritmo más simple. Usa una cola FIFO — quien llega primero, se ejecuta primero hasta que termina.

⚠️ Efecto Convoy: Un proceso muy largo bloquea a todos los demás. Si P1 dura 100ms y P2 dura 1ms, P2 espera 100ms innecesariamente.
⚡

SJF — Trabajo más corto primero

▼

Ejecuta el proceso con la ráfaga de CPU más corta. Es el algoritmo óptimo — minimiza el tiempo de espera promedio.

  • No apropiativo: Si llega proceso más corto, el actual termina primero.
  • Apropiativo (SRTF): Si llega proceso más corto que el tiempo restante, interrumpe inmediatamente.
⚠️ Problema: ¿Cómo saber cuánto durará la próxima ráfaga? Se usa estimación mediante promedio exponencial.
🔄

Round Robin — Turno por turno

▼

Cada proceso recibe un quantum de tiempo (10-100ms). Si no termina en su quantum, va al final de la cola.

  • Quantum grande: Se comporta como FCFS.
  • Quantum pequeño: Demasiados cambios de contexto → overhead mata el rendimiento.
  • Quantum ideal: Mayor que la mayoría de ráfagas de CPU.
💡 Ideal para time-sharing: Todos los procesos responden, nadie se queda esperando indefinidamente.
🏆

Planificación por Prioridad

▼

Cada proceso tiene un número de prioridad. La CPU va al proceso con mayor prioridad (número más pequeño = más prioridad).

💀 Inanición (Starvation): Procesos de baja prioridad pueden nunca ejecutarse si siempre llegan procesos de alta prioridad.
✅ Solución — Aging: Aumentar gradualmente la prioridad de procesos que esperan mucho tiempo. "Envejeces, subes de prioridad."

📊 Métricas de Evaluación

CPU Utilization

Mantener la CPU tan ocupada como sea posible. Objetivo: 40-90% en sistemas reales.

Throughput

Procesos completados por unidad de tiempo. Mayor = mejor rendimiento general.

Turnaround Time

Tiempo total desde que el proceso llega hasta que termina. Incluye espera + ejecución.

Waiting Time

Tiempo que el proceso pasa en la cola de listos. No incluye E/S.

Response Time

Tiempo desde que se envía la solicitud hasta la primera respuesta. Crítico en sistemas interactivos.

// 07 — BLOQUEOS

Deadlock — Bloqueo Mutuo

Un "punto muerto" donde ningún proceso puede avanzar porque todos esperan algo que otro tiene y no suelta.

Ejemplo del mundo real: Imagina que dos personas quieren cruzar un puente de un solo carril. Persona A está a la mitad, Persona B llega al otro extremo. Ninguno cede. Nadie avanza. → Deadlock.

Las 4 Condiciones Necesarias

Deben cumplirse todas simultáneamente para que ocurra un deadlock. Eliminar una = no hay deadlock.

01 🔐

Exclusión Mutua

Al menos un recurso debe estar en modo no compartido — solo un proceso lo usa a la vez. La impresora no puede ser usada por dos procesos simultáneamente.

02 🤲

Posesión y Espera

Un proceso ya tiene al menos un recurso Y está esperando obtener recursos adicionales que otros procesos tienen.

03 🚫

Sin Expropiación

Los recursos no se pueden quitar a la fuerza. Solo el proceso que lo tiene puede liberarlo voluntariamente cuando termine.

04 🔄

Espera Circular

Existe una cadena: P0 espera recurso de P1, P1 espera de P2, P2 espera de P0. Círculo cerrado = nadie avanza.

Estrategias para Manejar el Deadlock

🛡️

1. Prevención — Eliminar una condición

▼

Asegurar que al menos una de las 4 condiciones nunca se cumpla:

  • Atacar Espera Circular (más práctica): Forzar a los procesos a pedir recursos en un orden específico y global. Si todos piden recursos en orden R1→R2→R3, no puede haber ciclo.
  • Atacar Posesión y Espera: El proceso pide TODOS sus recursos antes de empezar. Difícil porque no siempre se sabe qué se necesitará.
🏦

2. Evitación — Algoritmo del Banquero

▼

El SO evalúa cada solicitud de recurso: ¿Si concedo esto, el sistema sigue en estado seguro?

Como un banco: solo presta dinero si puede garantizar que todos los clientes podrán devolver sus préstamos. Si la solicitud pondría el sistema en estado inseguro, se rechaza temporalmente.

Requiere conocimiento previo: Cada proceso debe declarar el máximo de recursos que podría necesitar. En la práctica, esto es difícil.
🔍

3. Detección y Recuperación

▼

Dejar que ocurra el deadlock, detectarlo periódicamente y recuperarse:

  • Abortar procesos: Matar todos los procesos en deadlock o uno por uno hasta romper el ciclo.
  • Expropiar recursos: Quitar recursos a algunos procesos y dárselos a otros.
🐦 Algoritmo del Avestruz: Windows y Linux a veces simplemente ignoran el problema si ocurre muy raramente, asumiendo que el usuario reiniciará.
